## Stack

## Dependencies

## Layout

```
app/main.py                   app wiring: CORS, exception handlers, routers
app/auth.py                   header-auth dependency + require_roles
app/config.py                 settings read from the environment
app/routers/<resource>.py     one APIRouter per resource; thin

```

## Layering rules

The HTTP layer binds and validates input and calls business logic; business logic owns the rules; data access owns queries and owns no rules. Request/response objects and persistence models stay distinct types even when their shapes coincide — mapping is explicit code.

## Persistence

PostgreSQL — the connection comes from `DATABASE_URL` in the environment; never hard-code credentials.

- Money uses `NUMERIC(18,2)` — never a float. Timestamps use `TIMESTAMPTZ`.
- Identifiers fold to lower case unless quoted; keep table and column names snake_case so nothing needs quoting.
- Use `JSONB` (not `JSON`) when a column holds structured data — it is indexable.
- Schema changes go through migrations, applied at startup. Never auto-create the schema in a production path.
- Seed only reference/lookup data, and make seeding **idempotent** — it runs on every start, so guard each insert with an existence check or restarts duplicate rows and trip unique constraints.

- Response field names must match the frontend's types **exactly**, including suffixes.
  `hiringManagerName` and `hiringManager` are different fields. A mismatch produces a 200
  response with blank fields on screen, not an error, so it is invisible without diffing the

- Implement exactly the paths, methods and role lists listed below. Do not invent variants.
- JSON property names on the wire are **camelCase**.
- Paged endpoints accept `page`/`pageSize` (plus `search`/`sortBy`/`sortOrder` and the
  endpoint's filters) and return the contract's paged response shape.
- Errors use ONE shared body — `{ "error": string, "details": string[] }` — produced by a
  single error-handling layer, never hand-rolled per endpoint.
- Status codes: 200 OK, 201 Created (+ Location), 204 No Content, 400 validation, 401 missing
  auth, 403 wrong role, 404 not found, 409 conflict.

## Authentication (header stub — no identity provider)

There is no login or token flow here. Callers send `X-User-Role` and `X-User-Id`. Missing role
header → **401**; role not permitted for that endpoint → **403**. Owner/assignment checks use
`X-User-Id`, not the role alone. Do not build login, tokens or user tables. The permitted role
names are exactly those in the Roles column of the endpoint table below — do not invent a role
that the contract does not name.

**Both headers must be declared to the API documentation/OpenAPI layer as security schemes.**
If they are not, the generated docs UI shows no authorize input and sends no headers, so
every "try it out" call comes back 401 while the API itself is fine. This has already cost a
debugging cycle once — keep the declarations wired.

## CORS — the frontend is a different origin

Configure CORS for the frontend origins, read from configuration, allowing the request
methods, `Content-Type`, and the `X-User-Role`/`X-User-Id` headers.

Two rules that are easy to get wrong and produce blank screens rather than API errors:
- If credentials are allowed, the allowed origins must be **explicit** — "allow credentials"
  combined with "allow any origin" is rejected at runtime by most frameworks.
- The CORS layer must run **before** authentication/authorization in the middleware order,
  or the browser's preflight request is rejected before the policy is ever applied.

## Identifiers — the same format on both sides

Ids in this project are **UUIDs**. Every id field -- primary keys, path parameters, request bodies, response bodies, foreign keys -- is a UUID.

- Type these columns as the database's native uuid type (`uuid` on PostgreSQL, `uniqueidentifier` on SQL Server, `CHAR(36)`/`BINARY(16)` on MySQL), and type the matching path/body parameters as a UUID type too, so a malformed id is a **400 at validation** rather than a driver error.
- Never accept or emit a human-readable key (`USR-0001`, `JOB-42`, `ORD-7`) where a UUID is expected. A uuid column rejects it at the driver, not at validation, so it surfaces as `invalid input syntax for type uuid` -- a 500, not a 400.
- Generate ids server-side: a database default (`gen_random_uuid()`, `newid()`) or the app layer at insert time. **Never accept an id from the client on create**: a POST body carries
  no id, and the generated id comes back in the response (201 + `Location`).
- Never hard-code a specific id, in code or in seed data. Ids come from the database,
  from route params, or from a previous response.
- The backend's DTOs and the frontend's typed models declare id fields with the same
  name and the same type. If they disagree, the contract wins.
